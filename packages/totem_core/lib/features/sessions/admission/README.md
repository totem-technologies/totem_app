# Client-side Session admission

Admission is cooperative, **not a secure authorization boundary**. The existing join endpoint grants access to the actual LiveKit room; a modified client can subscribe to remote media or bypass this UI. Pending clients connect with `autoSubscribe: false`, do not publish tracks, and only render their local pre-join preview. The server's speaking-order reconciliation still sees connected pending clients; the application cannot safely rewrite backend-owned talking order or room metadata to remove them.

Packets on `totem.admission.v1` use reliable, targeted LiveKit data and authenticate the sender against the LiveKit event identity. Requests expire two minutes after creation (not at the Session join cutoff). Keeper reconnect hello packets and participant presence events cause one-shot retransmission of the same request ID. Packets are **not persisted**: a fully terminated participant app starts a new attempt, a fully terminated Keeper loses its in-memory decisions, and independent Keeper devices are not synchronized. A sent approval is not an acknowledgement that the participant joined successfully. Keeper `requests` remains the actionable pending queue; `attempts` also exposes `requested`, `joining` (with `joinDeadline`), `joined`, `joinFailed`, `timedOut`, `denied`, `cancelled`, and `expired` snapshots for the latest attempt per identity. An approval stays `joining` until an authenticated matching receipt arrives or the original request expiry passes. Snapshots are in-memory and cleared on room end or replaced by a later attempt.

Joining starts ten minutes before the scheduled Session for participants; Keeper entry remains available as before. The existing backend independently determines eligibility and can reject first-time joins after its own cutoff, including before the design's T+15 target. No client timer or UI can extend server eligibility. Pending room connections are closed before normal Session join to avoid simultaneous LiveKit connections, while the existing local preview tracks remain with the pre-join media controller until the Session controller takes ownership. This incurs one reconnect after approval rather than adopting an already-connected room. After approval, the pre-join flow closes the admission connection, refreshes server join authorization, then transfers the local preview tracks to `SessionController.join`. Only once the normal connection succeeds does `SessionMessagingController.sendAdmissionJoined` publish the original request ID to the Keeper on the admission topic. The normal room owns that separate transport until teardown; it retries the receipt on Keeper hello, presence, or room reconnect, until request expiry, without polling. If authorization or connection fails before the normal room connects, there is no channel to send a failure receipt; the Keeper eventually marks the attempt `timedOut` and the participant can retry through the entry flow. If normal join fails before connecting, no failure receipt can be sent; Keeper eventually marks the attempt `timedOut`.
